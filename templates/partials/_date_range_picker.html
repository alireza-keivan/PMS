{% load i18n %} {% comment %} Pick the whole stay - the "Date Range Picker" card from the design handoff. One field, not two. The visitor sees a single box reading "12 Sep - 15 Sep, 3 nights"; tapping it opens the calendar, where the two ends of the stay are set by picking a start and an end. Inside the calendar the design's two tabs say which end the next tap sets, and the nights in between are shaded. Reusable on purpose. Anywhere two date fields form a stay, include it as: {% include "partials/_date_range_picker.html" with ci_field=form.check_in co_field=form.check_out %} Optional extras: min_nights shortest stay, so the leaving date can't be picked too early (default 1) dates_label the label on the one field (default "Dates") booked_nights_id id of a json_script holding the nights that are already taken - {"any": ["2026-09-04", ...], "": [...]}. Those days come up greyed out and cannot be picked. room_select_name name of the room picker on the same form, when there is one: which list above applies depends on the room chosen, so the calendar redraws when that select changes. picker_id only needed if two pickers ever share one page How it works, and why it's built this way: the two real date inputs are always here and always submitted. With no JavaScript they show as ordinary date boxes and the form works exactly as before - the visitor is on 4G on a phone and nothing on the public villa page is allowed to depend on a script. When the script does run it hides those boxes, shows the single field, and writes back into the same inputs (firing `change`, so the price line listening on them still updates). So the inputs stay the one source of truth; the calendar is only a nicer way to fill them in. {% endcomment %}
